# Proposal

## Why

当前敏感词匹配只对原文执行大小写不敏感的连续子串查找，用户可通过插入空格、零宽字符、标点、字母、数字或汉字绕过实时拦截和历史巡检。项目现有 `content-moderation` 规范已要求支持拆字、全角半角等常见变体，需要补齐可验证且有明确跨度边界的匹配行为。

## What Changes

- 对内容和敏感词执行 Unicode NFKC 与大小写归一化，统一全角半角及兼容字符。
- 将敏感词匹配从连续子串扩展为有界插入匹配：相邻敏感词字符之间允许最多 3 个普通 Unicode code point，且总共最多跨过 16 个 Unicode code point。
- 插入字符可为空白、格式字符、标点、符号、Emoji、字母、数字或汉字；规则不提供语境白名单或普通含义豁免。
- 保留归一化匹配位置到原文位置的映射，使历史巡检预览仍从正确的原文区域生成。
- 实时发帖、编辑话题、回复和编辑回复命中后继续返回现有 `422` 响应且不写入内容；历史内容继续写入现有巡检队列。
- 为连续命中、各类插入绕过、跨度边界、Unicode 位置映射、误匹配边界和 10000 字性能预算增加验证。
- 发布后由管理员显式创建一次全量历史巡检任务，使已有敏感词按新规则重新检查历史内容。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `content-moderation`: 明确敏感词变体归一化、有界插入匹配、严格拒绝语义、原文位置映射和历史重扫要求。

## Scope

### In scope

- `apps/api/src/lib/moderation.ts` 中由实时过滤和巡检共用的匹配行为。
- `apps/api/src/lib/moderation-scan.ts` 中依赖命中位置生成原文预览的流程。
- 匹配器单元测试、相关 API 行为测试和性能测试。
- 使用现有管理员巡检能力执行发布后的全量历史重扫。

### Out of scope

- 拼音、同音字、同形字、编辑距离或模型语义审核。
- 按词条配置不同匹配策略、白名单或语境豁免。
- 修改敏感词表结构、巡检任务表结构或管理后台页面。
- 自动删除或隐藏历史命中内容。

### Affected systems

- API 的话题和回复创建、编辑路径。
- moderation worker 的历史与增量巡检路径。
- 敏感词命中计数、巡检命中预览和去重流程。

### High-risk categories

- **误拒绝**：短敏感词配合插入匹配会扩大命中范围；本变更按已确认政策不提供普通语境豁免，并以 3/16 双边界限制跨距。
- **性能**：长内容与大词库的匹配成本可能增加，必须继续满足现有 10000 字内容低于 100ms 的规范预算。
- **Unicode 下标**：NFKC、代理对和组合字符可能改变长度，错误映射会导致巡检预览偏位。
- **历史结果变化**：重新巡检会产生过去未发现的待复核记录，但不得直接处置原始内容。

## Impact

- 外部 API 结构和状态码不变，但过去可发布的插入变体将改为返回 `422`，属于有意的内容接受规则收紧。
- 预计不新增运行时依赖；实现应优先使用 JavaScript Unicode 标准能力。
- 不需要 PostgreSQL schema、迁移、回填或数据修复。
- `moderation_hits` 的现有去重键和 `sensitive_words.hit_count` 语义保持不变。

## Documentation Impact

- `docs/biz/community-rules.md` 是适用的长期业务规则文档，需要说明严格敏感词命中及 3/16 有界插入规则。
- `docs/arch/` 与 `docs/deployment/` 无需更新，因为架构、拓扑和部署方式不变。
- 根治理文件与 `apps/*/README.md` 无需更新。
- API 响应结构未变化，`apps/web/public/openapi.json` 无需因本变更更新。
- 文档任务适用 `cnode-docs`，实施时需先确认权威文档归属并执行对应验证。

## Non-goals

- 建立无法绕过的通用语义审核系统。
- 根据敏感词在句子中的含义决定放行或拒绝。
- 改造管理后台词库模型或提供逐词匹配模式开关。
- 让历史巡检命中绕过现有人工复核流程。
