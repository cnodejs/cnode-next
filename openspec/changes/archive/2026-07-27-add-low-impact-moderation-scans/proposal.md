## Why

当前敏感词只在新发和编辑内容时拦截，新增敏感词后不会检查历史话题和回复；后台“巡检结果”也只读取 `topics.status = muted`，缺少真正生成巡检结果的扫描流程。为了替代 legacy nodeclub 的人工运营能力，并避免一次性全库扫描影响线上服务，需要引入低负载、可恢复的历史和定时巡检机制。

## What Changes

- 新增低负载内容巡检任务：按批次扫描历史 `topics.title`、`topics.content`、`replies.content`，不把全量内容加载进内存。
- 新增巡检命中队列：记录命中对象、命中词、上下文预览、扫描来源、处理状态和审计信息。
- 添加敏感词后自动创建针对新增词的历史扫描任务，管理员也可手动创建全量或增量扫描任务。
- 新增定时增量扫描能力，周期性检查新增或更新的已发布话题和回复。
- 后台“巡检结果”改为展示巡检命中队列，支持话题和回复的确认删除、标记误报、忽略/恢复等处理动作。
- 扫描任务必须可暂停、可恢复、可限速，并使用单实例锁避免重复执行。

## Non-goals

- 不在用户读取话题/回复时动态执行敏感词扫描，避免增加线上读路径延迟。
- 不在添加敏感词 API 请求内同步扫描全库，避免请求超时和服务资源争用。
- 第一阶段不默认自动删除历史命中内容；历史命中先进入巡检队列，由管理员复核。
- 不迁移 legacy nodeclub 中不存在的复杂风控判定模型；本变更只围绕敏感词扫描和巡检复核闭环。

## Capabilities

### New Capabilities

- `moderation-scan-jobs`: 低负载历史和定时内容巡检任务，包括任务状态、进度游标、限速、恢复和单实例执行约束。

### Modified Capabilities

- `content-moderation`: 将现有敏感词巡检需求具体化为扫描任务和命中队列，覆盖历史话题和回复。
- `admin-dashboard`: 后台巡检结果从 `muted topic` 占位页改为展示可复核的 topic/reply 命中队列和扫描任务状态。
- `anti-spam`: 巡检命中和管理员处理结果进入审计日志，作为后续渐进式封禁的输入信号。

## Impact

- 影响后端 API：`apps/api/src/routes/admin.ts`、敏感词管理、巡检结果 API、审计日志写入。
- 影响后台 Web：`apps/web/app/routes/admin/mod.tsx`、敏感词页面和管理概览统计。
- 影响数据库：新增巡检任务表、巡检命中表，必要时补充 reply 处理所需字段或索引。
- 影响部署：新增独立 worker 进程或 compose service，用于执行扫描任务和定时调度，避免 API 进程承担重任务。
